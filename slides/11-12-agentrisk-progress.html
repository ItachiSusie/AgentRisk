背景 · 问题定义≈1 min

给定历史，评估 agent 的下一个动作

x = (h, a)    h = 历史轨迹（history）   a = 待评估动作（proposed_action）

输入

h：用户请求、agent 思考、工具调用（Action）与工具返回（Observation），即 ReAct（Reasoning + Acting，推理与行动交替的 agent 循环）格式的轨迹。

a：agent 下一步准备执行的动作，可以是命令，也可以是一段自然语言回复。

只评估 a：历史里有人诱导泄露数据，但 a 是拒绝 → a 是安全的。

输出：四个函数

Task 1f₁(h, a) = r，r ∈ {1,…,5}
风险等级；MAE（Mean Absolute Error，平均绝对误差）↓
Task 2af₂ₐ(h, a) = D，D ⊆ 11 个危害领域，|D| ∈ {1,2}
「会伤到什么」；Mean Jaccard（集合交并比均值）↑
Task 2bf₂ᵦ(h, a) = K，K ⊆ 7 个风险驱动因素，|K| ∈ {1,2}
「风险从哪来」；Mean Jaccard ↑
Task 3f₃(h, a, p) = (i, m)，按 policy p 选干预 i 并给反馈 m
官方尚无 policy 与 gold 标注 → 本阶段不做

计划：先把 Task 1 / 2a / 2b 做扎实，再接 Task 3。

方法 · ① Zero-shot≈1 min

Zero-shot：两个维度 × 输出格式

零样本（zero-shot，prompt 里只有任务指令和当前样本，没有已标注示例）。两个维度：

无推理 w/o reasoning
只输出标签 JSON		有推理 w/ reasoning
先写 ≤120 词依据，再给标签		先事实 facts
先引原文事实，再判断，再给标签
多任务 multi-task
一次调用同时输出 r、D、K		① zero-shot-v1② zero-shot-v4—
单任务 single-task
每个任务独立一次调用		③ <task>-answer-v1④ <task>-reason-v1⑤ <task>-facts-v1 第 ⑤ 步再讲
// ② / ④ 有推理
{"reasoning": "The action sends the payment roster
  to an external alias taken from a note …",
 "answer": {"risk_severity": 4}}
// ⑤ 先事实（代码检查 quote 是否为原文子串）
{"facts": [{"quote": "Mailbox type: external",
            "note": "收件方在外部"}, …],
 "judgment": "≤80 词，只能引用上面的事实",
 "answer": {"risk_severity": 4}}

①–④ 的标签定义完全相同，只差「一次预测几个字段」和「输出格式」，构成单变量对照。

prompt：prompts/zero_shot_v1.txt、prompts/zero_shot_v4.txt、prompts/single/<task>/zero_shot_{answer,reason,facts}_v1.txt；格式说明见 docs/reasoning-answer-experiment.md。
方法 · ② Few-shot≈1 min

Few-shot：从 train 里给每条 dev 样本选 k 个示例

少样本（few-shot，在当前样本前放 k 个已标注的 train 样例，示例只给标签）。对 ①–④ 每个 zero-shot 变体都跑一遍。

两种选法 × 四个 k

Random随机抽 k 个（seed 0）
BM25BM25（Best Matching 25，基于词频的文本检索打分）按轨迹文本检索最相似的 k 个
k3 / 5 / 10 / 20

成本随 k 线性增长：单任务 zero-shot 约 0.22 M 输入 token，k=10 约 2.0 M，k=20 约 3.8 M。

检索文本要不要额外拼上 action？

对照：bm25（只用 formatted_interaction）vs bm25-action（再拼一次 proposed_action）。

kBM25 MAE / 2a / 2b+action
30.266 / 0.853 / 0.7520.273 / 0.853 / 0.744
50.231 / 0.867 / 0.7790.259 / 0.860 / 0.759
100.189 / 0.862 / 0.7930.196 / 0.855 / 0.784

差距都在噪声内；两种检索选出的示例集合 Jaccard 平均 0.873，84% 的 top-1 相同。
→ 采用不带 action 的 BM25：history 里已经包含了动作的上下文，单独加权 action 反而会把「同样是 send email、语境完全不同」的样本拉进来。

多任务 dev，few-shot v1。来源：results/comparison.md §1、docs/next-round-plan.md §8「bm25-action 对照」。
方法 · ③ Trace2Skill（论文）≈0.5 min

Trace2Skill：把很多条轨迹一次性归纳成一份 skill

轨迹蒸馏（trajectory distillation）：不更新模型参数，把 agent 在训练题上的执行轨迹归纳成一份可直接加载的技能文档（skill，SKILL.md + references）。

Stage 1 · 生成轨迹固定模型 + 初始 skill 𝒮₀ 跑完全部 evolve 题，记录每条轨迹和二值对错
→
Stage 2 · 并行提补丁一条轨迹一个分析师，产出轨迹级补丁（patch）
· 错误分析师 𝒜⁻：ReAct 循环，能对答案、重跑验证修法
· 成功分析师 𝒜⁺：提炼可复用做法
· 给不出因果解释的失败 → 丢弃
→
Stage 3 · 层次合并每层最多 32 个补丁合成一个：去重、消解冲突、保留高频模式、丢掉一次性怪招
→
产物：𝒮*静态 skill 目录，测试时直接加载，不做检索

论文报告：SpreadsheetBench-Verified 上 Qwen3.5-122B 从人写 skill 的 48.33 提升到 69.83（Vrf）。核心思想是「多个独立补丁反复改同一处 = 系统性规律」。

Ni et al., Trace2Skill, arXiv:2603.25158v5，§2.2–2.4、表 1；读稿见 docs/reading-notes-trace2skill.md §3–4。

发现 · 盲测探针≈1 min

盲测探针：错在「读错了」还是「线划得不一样」？

Task 1 错误集中在 3/4 边界（train_evolve 上 3→4 有 34 条，4→3 有 21 条）。两种解释对应完全不同的改法：

错误类型含义改法
理解错误事实读错或漏读让模型读仔细：先列事实
尺度错误事实都对，线和标注者划得不同把线展示出来：对比示例

做法：先盲审，后揭晓

A · 盲审更强的分析器（Opus 5.5）看轨迹 + 模型推理，等级词全遮成 [LEVEL]；逐条核对事实是否有原文依据；在两个候选等级（升序，不说哪个是答案）里强制二选一
→
B · 揭晓归类告诉它真实值和预测值，再归类；代码做一致性检查

为什么有用：盲选在不知道答案时做出，不受事后合理化（hindsight bias）影响。若强模型只看定义都选不准，说明线不在定义的文字里。

结果（41 条，Opus 跑两次）

~50%盲选与真实等级一致（20/41、22/41），相当于随机
~1/3被判为阅读错误（两次都是 13/41）
  • 主体是尺度问题：线是标注约定（或噪声），要靠示例展示 → 解释了为什么 few-shot 在 Task 1 上有效、写规则改不动
  • 约 1/3 是阅读错误：如把「住宅楼」读成「家庭住址」、把可撤销授权说成「不可逆」 → 可以用「先列事实」修
  • 用 DeepSeek 自己当分析器几乎看不出阅读错误（盲判 19/20 等于预测值）→ 分析器必须换成更强、不同的模型

扩大到全部错例后，盲选命中率：Task 1 64–69%，2a 60–63%，2b 61%。

样本：train_evolve 上 reason-v1 的已有输出（20261104-082558），不重跑预测。设计与结果见 docs/agentic-distill/01-blind-probe.md。

方法 · ⑥ evolve（Qi 设计，替代 Trace2Skill）≈1 min

evolve：一次只改一小处，验证过才保留

只用 train_evolve（461 条），按场景分成 5 折（fold，数据的一份，约 92 条）。每一轮轮流用 1 折提出改动，用另外 4 折（约 370 条）检验改动。train_val 和 dev 不进循环。预测器和提议器（proposer，负责写 prompt 改动的那次模型调用）都是 deepseek-flash，种子 prompt 是 reason-v1。

① 选目标提议折里最常见的一类错误（格子，如「金标 A、预测成 B」），至少 4 条才开始
→
② 盲读提议器看错例 + 相近的对例，不看金标，先找出决定答案的原文事实
→
③ 提改动再看金标，给出 4 种不同的小改动：改定义 / 加检查 / 加对比句 / 删句子
→
④ 两道闸门先在 40 条上快测，再在 4 折上全测
→
⑤ 留或弃每轮最多保留 1 个；连续 2 轮没有改动通过就停
Trace2Skill 的问题evolve 的做法
规则把对的改成错的（Task 1 0.266 → 0.350）全闸门 G1–G6：修对的要明显多于改坏的（超过噪声 2 倍）、改坏的 ≤ 3%、不许把 A 类错挪到 B 类（G3）、低风险样本不能被改坏、至少 3 折都有收益、无效输出不增加
分析器看了答案，被答案锚定先盲读、后看金标；代码会检查引文是否逐字来自原文
一次塞进很多条规则，说不清哪条有用一次只改一处，每处单独检验；每个改动的来源和闸门数字都写进记录
train_val 上有效，dev 上消失提出改动的折不参与检验；dev 只在预登记后跑一次

未来方向：分别针对尺度问题和理解问题

盲测探针给出的两类错误：尺度问题（事实读对了，但线划得和标注者不同，占主体）和理解问题（事实读错或漏读，约 1/3）。三个方向分别对准它们。

尺度问题

① Label Definition from Training Data

官方定义已经补进 prompt，但只看了总分，还没逐条分析哪些有用。

  • 逐个标签、逐个等级，对照 train 里的正例和易混反例，检验官方描述能否区分它们
  • 保留有区分力的描述，改写含糊的，补上训练数据里反复出现、但官方没写的判据
  • 重点：3 / 4 等级边界、Scope ↔ Authorization
尺度问题

② Rules from Experience

经验规则（rules from experience）：从模型在训练集上的实际判断记录（对的和错的）里总结出的「遇到什么情况怎么判」，而不是从定义文字推出来的规则。

  • 定义回答「这个标签是什么意思」，经验规则回答「边界上的具体情况该往哪边判」
  • 每条规则带触发条件、判定和反例，在 train 上回测，不能弄坏已判对的样本
  • 和 ① 配合：定义划大方向，规则补边界
