# AgentRisk 三轮实验路线

更新日期：2026-10-30 · 状态：计划，尚未代表已完成实验

## 目标与共同约定

先建立 API 大模型基线，再用 traces2skill 提炼可复用的 Agent Risk Guardian Skill；随后研究已有模型微调及数据扩展，最后根据 dev 结果和正式比赛规则确定提交方案。

当前优先覆盖 Task 1、2a、2b，分别报告 MAE（越低越好）、domain Mean Jaccard 和 driver Mean Jaccard（越高越好），不自行将三项指标合成官方总分。Task 3 待官方 policy、数据和评测要求齐备后接入。数据数量、指标和规则以运行时固定的官方版本为准。

这里将 traces2skill 作为待实现的方法路线：从交互轨迹、模型判断及其错误中，提炼有证据支持、可跨场景复用的风险评估步骤。具体工具或论文实现尚未指定。Guardian Skill 是供风险评估模型使用的指令知识，不直接执行轨迹中的工具动作。

## 第一轮：API 大模型与 Guardian Skill

### A. 建立 zero-shot → few-shot 基线

沿用 [LLM In-context Learning Solution](llm-in-context-learning-solution.md) 的 DeepSeek API 起点；正式运行前确认实际可用模型及参数，保存模型标识和运行日期。Shuai lead 接入、推理与评测；instruction 与结果分析沿用现有协作分工。

1. 固定数据 revision、样本 ID、scenario group 和评测程序。
2. 使用少量 train 样本完成输入、输出和费用记录检查。
3. 冻结 zero-shot prompt，跑完整 dev，保存原始响应、合法预测、指标和失败记录。
4. 从 train 选择固定 few-shot 示例，记录 ID 与选择依据，保持其余配置一致后评测。

### B. 用 traces2skill 提炼 Guardian Skill

1. 在 train 内按官方 scenario group 划分开发折与验证折；同场景的安全、危险对应样本必须在同一折。
2. 收集开发折中的轨迹、gold 标签、模型预测和简短的证据说明。证据说明应指出相关步骤及判断依据，不要求获取模型隐藏思维链。
3. 归纳错误类型和可复用规则，例如：最终动作与历史危险请求的区分、授权来源、工具输出中的不可信指令、直接损害与推测后果、风险等级边界。
4. 将规则整理为 skill 草案：适用范围、评估流程、domain/driver 选择准则、边界案例、结构化输出要求。每条规则保留来源 train ID 和修改记录。
5. 在未参与提炼的 train 验证折检查泛化，删除依赖姓名、场景措辞或个别标签答案的规则。确定方法及版本后，才进入完整 dev 对照。

“Zero-shot + skill”表示推理时不附带标注示例，但 skill 由带标签的 train 提炼，报告中应明确其数据使用，不能称为完全未使用训练数据。

### C. 四组核心对照

| 实验 | Few-shot 示例 | Guardian Skill | 要回答的问题 |
| --- | --- | --- | --- |
| A0 | 无 | 无 | 原始 zero-shot 性能如何？ |
| A1 | 固定 train 示例 | 无 | 示例本身带来多少收益？ |
| A2 | 无 | 有 | Skill 能否改善不带示例的推理？ |
| A3 | 与 A1 相同 | 与 A2 相同 | Skill 与 few-shot 是否互补？ |

保持模型、数据、解码参数、输出格式和失败处理一致；分别比较 A2 对 A0、A3 对 A1。记录实际完整 prompt、skill 与示例版本、输入输出 token、费用、延迟和合法输出率。若有改善，再用简短通用风险检查清单作为对照，检查收益是否来自提炼内容；必要时做 skill 组成部分的消融。

完成标准：四组均覆盖完整 dev，三项指标可复算；skill 规则可追溯到 train；能说明改善和退化发生在哪些错误类型。提升是待验证假设，结果不佳也保留并报告。

## 第二轮：先微调，再研究 augmentation 与扩展

### A. 仅用已有官方数据微调

选定一个已有的小型指令模型，以资源预算和轨迹长度为依据确定规模；优先采用 LoRA/QLoRA 等参数高效微调方式。先检查完整输入能否容纳，不静默截断关键上下文。

| 实验 | 训练数据 | 推理设置 |
| --- | --- | --- |
| B0 | 不微调 | 基础模型 + 固定任务 instruction |
| B1 | 仅官方 train | 微调模型 + 与 B0 相同的 instruction |
| B2 | 仅官方 train | 微调模型 + Guardian Skill |

B2 应使训练与推理的 skill 条件一致，并说明与 B1 的差异；训练标签、输出格式和训练预算尽量一致。超参数与训练轮数在 train 的分组验证中选择，记录随机种子、checkpoint 和完整训练配置。优先使用官方标签构造结构化监督目标；若加入解释或教师输出，另记为独立实验及伪标签来源。

### B. 在原始数据基线上研究数据扩展

完成 B1 后再决定是否扩展，优先针对 train 分组验证暴露的不足提出假设：

- **保持标签的改写**：替换实体、工具表述和非关键措辞，同时保留授权、后果和可逆性等风险条件；改写后仍需复核标签。
- **改变风险条件的对照**：改变是否获授权、是否存在确认、动作范围或可逆性，构造安全与危险配对，并重新标注。
- **扩展新场景**：围绕覆盖不足的 domain、driver 或组合生成新轨迹，检查情境合理性、标签证据和与官方任务的一致性。

每条扩展样本保存父样本/场景 ID、生成配置、变换类型、标签依据和审核状态。去除重复、矛盾和缺少风险证据的样本；原始场景及其全部派生样本在内部验证中归为同组。模型生成的标签不自动视为 gold，先人工抽检，边界案例重点复核；必要时扩大审核或弃用该批数据。

先在可控规模上做原始数据与扩展数据对照，固定基础模型、训练方法，并记录数据量和训练 token；另设训练预算匹配对照，区分扩展内容与额外训练量的收益。不因规模增加就默认质量提高。

完成标准：原始数据微调结果可复现；若实施扩展，须有数据来源、审核和去重记录，以及相对 B1 的独立对照。若只有少量或不稳定收益，不继续无目标扩大数据。

## 第三轮：选型、冻结与提交

1. 读取正式比赛规则，逐项确认 API、模型规模、外部/合成数据、教师模型使用、提交形式、调用预算及可复现材料要求；当前未明确的内容不视为已获官方允许。
2. 汇总第一、二轮候选，分别比较三个子任务指标、train 分组验证、dev 表现、合法输出率、费用和延迟。规则允许时可为不同子任务选择不同方案。
3. 对接近的候选按 scenario group 做配对 bootstrap，估计指标差值的不确定性；对随机性较明显的候选补充种子或重复运行。Dev 规模较小，不凭单次微小涨分作强结论。
4. 冻结最终模型/checkpoint、prompt、skill、few-shot ID、数据版本与配置。按正式格式检查提交文件，整理系统描述、消融实验和资源成本。

完成标准：得到符合正式规则、完整预测可复算、版本可追溯的最终系统和提交材料。

## 数据边界与实验记录

- Few-shot 选择、skill 提炼、训练、augmentation 种子与生成提示只使用 train；不将 dev 样本或 gold 写入 skill、训练集或扩展数据。
- Dev 可以用于已声明的候选比较和汇总错误分析；具体规则和样本修复在 train 上实现与验证。记录查看 dev 后的每次修改，承认重复开发会带来选择偏差；最终泛化结论依赖正式测试。
- 所有实验保存 run ID、数据 revision/hash、模型标识、prompt/skill hash、示例 ID、训练配置、逐条预测、原始响应、三项指标、失败率和资源消耗。合成数据另存生成与审核记录。
- 第一轮 API baseline 的具体输出目录和文件规范继续遵循 [执行文档](llm-in-context-learning-solution.md)。
