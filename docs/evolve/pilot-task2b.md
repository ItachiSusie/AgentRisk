## 2. 噪声底

噪声底 τ（noise floor）指同一个 prompt 在 temperature 0 下跑两遍、预测不一致的样本数。

| 规模 | τ | 两遍之间损失变好 / 变坏 | 来源 |
|---|---|---|---|
| 试跑 2，150 条 | 26（17.3%） | 9 / 8 | `20261111-091240/baseline.json` |
| 试跑 3，250 条 | 39（15.6%） | 11 / 10 | `20261111-100017/baseline.json` |
| 完整 train_evolve，461 条 | 78（16.9%） | 17 / 17（370 条评估样本上） | 两次已有的 reason-v1 运行，见下 |

完整规模的数字来自主仓库里两次 prompt 完全相同的 reason-v1 运行：`results/_smoke/task2b/zero-shot-reason-v1/20261104-093411` 和 `20261110-030342`（sha256 都是 `4fffb391…`）。复算命令：

```bash
python src/evolve_pilot_check.py noise --a <主仓库>/results/_smoke/task2b/zero-shot-reason-v1/20261104-093411 --b <主仓库>/results/_smoke/task2b/zero-shot-reason-v1/20261110-030342
```

结论：deepseek-flash 在 temperature 0 下大约每 6 条就有 1 条两次答案不同，三种规模的结果一致。但噪声的方向是对称的，两遍之间的**净**修正数只有 0–1。

## 3. 两个调整建议，离线判断都不可行

下面两个改法都不需要重跑：闸门只是在已缓存的预测上做计算，所以直接拿第 3 次试跑的现有候选回放即可。

### 3.1 `min_wrong` 从 4 降到 3 或 2：不需要

`min_wrong` 指一个错误格子至少要有几条错例，才能被选为这一轮的目标。

- 它只在试跑规模很小时才会卡住。每折 10 条和 30 条时，第 1 轮用到的第 1 折里最大的格子分别只有 2 条和 3 条，所以被跳过。
- 每折 50 条时，两轮都正常选出了目标，`min_wrong=4` 已经不是瓶颈。
- 完整规模下，每折最大的格子（金标 Scope / Safeguard Failure，预测成 Authorization / Consent Failure）都有 9–11 条。全量运行总是先挑代价最高的格子，降低 `min_wrong` 不会改变全量的结果。

### 3.2 G1 从 2 倍噪声降到 1 倍：仍然会拒绝全部候选

G1 规定：净修正数 ≥ max(`min_net`, 2·τ_scaled)，并且改善概率 ≥ 0.9。其中 τ_scaled 是把 τ 按评估样本数缩放后的值。

| G1 门槛 | 要求净修正数 | r01c1（净 9） | r02c4（净 3） |
|---|---:|---|---|
| 2·τ（spec 现值） | 62.4 | 拒 | 拒 |
| 1·τ | 31.2 | 拒 | 拒 |
| 1·τ，τ 只算损失真正变化的样本 | 16.8 | 拒 | 拒 |

最好的候选 r01c1 只净修正 9 条，离 1 倍门槛还差三倍多。完整规模下，1·τ 对应约 63 条，而种子在 370 条评估样本里一共只错了 134 条。所以降到 1 倍仍然等于拒绝所有局部改动。

根本原因在于口径：噪声条数虽然多，但方向对称，两遍之间的净值接近 0。拿候选的**净**修正数去和噪声的**总**条数比，不管乘 2 还是乘 1，门槛都会偏高。

复算命令：

```bash
python src/evolve_pilot_check.py replay --run-dir results/evolve/task2b/20261111-100017
```
