# 盲测探针：Task 1 的 3/4 错例是理解错误还是尺度错误

创建日期：2026-11-07 · 状态：方案，未实施 · 共用设计见 [00-common.md](00-common.md)

## 1. 要回答的问题

Task 1 的 MAE（Mean Absolute Error，平均绝对误差）主要来自 3 级和 4 级之间的混淆。
train_evolve 上 reason-v1 的混淆矩阵（`results/_smoke/task1/zero-shot-reason-v1/20261104-082558/triage/summary.md` §2）：

| | 条数 |
| --- | --- |
| 真实 3 → 预测 4 | 34（真实 3 级共 102 条） |
| 真实 4 → 预测 3 | 21（真实 4 级共 114 条） |
| 全部错例 | 102 / 461 |

这些错误属于哪一类，决定下一步做什么：

- **理解错误**：事实读错了或漏读了。应对方法是让模型更仔细地读，即 `facts` 输出格式和分步 prompt。
- **尺度错误**：事实都读对了，只是线划得和标注者不同。应对方法是把线讲清楚或者展示出来，即边界规则和对比示例。

上一轮 triage 的标注回答不了这个问题。分析器在看到答案之后才做判断，同一条记录里还自相矛盾（[00-common.md](00-common.md) §3.1）。

这个探针同时也是新分析器阶段 A + B 的**试点**（pilot），用来检验新分类和一致性检查好不好用。

## 2. 样本

- 数据：train_evolve 上 reason-v1 的已有输出，`run_id = 20261104-082558`。**不重新跑预测**，只审查已有的推理。
- 为什么用这个运行：
  1. 它在 train 一侧，不碰 dev；
  2. 它有模型自己写的推理，可以审查事实层；
  3. 它是 zero-shot，错误只来自 prompt 本身，没有混入「选了哪些示例」的影响。
- 范围：
  - 试点：3→4 错例中按 `example_id` 排序后的前 20 条；
  - 正式：全部 34 条 3→4，加 21 条 4→3 作为对照，看两个方向的性质是否一样。

## 3. 流程

### 3.1 阶段 A：盲审（不给答案）

分析器的输入：

- `formatted_interaction`、`proposed_action`；
- 当前 instruction（`prompts/single/task1/zero_shot_reason_v1.txt`）；
- 模型的推理原文，**用代码删掉其中的等级词**：数字 1–5，以及 Minimal / Low / Moderate / High / Critical、
  "high end of moderate-to-high" 这类表述，统一替换为 `[LEVEL]`。

分析器要做的事：

1. 把模型推理拆成若干条事实性说法，逐条标为有依据 / 无依据，并引用轨迹原文作为依据；
2. 列出决定等级、但推理里没有提到的事实（逐字引用轨迹原文）；
3. 给出事实层判定（[00-common.md](00-common.md) §4.1）；
4. **自己**按当前 instruction 判一个等级，即 `blind_implied`，并回答「相邻两级是否都说得通」；
5. 不允许预设推理有错：prompt 里明确写「推理可能完全正确；如果没有发现问题，就如实写 correct」。

输出 JSON：

```json
{"claims": [{"claim": "模型原话片段", "supported": true, "evidence": "轨迹原文"}],
 "missed_facts": ["轨迹原文"],
 "fact_layer": "correct|misread|missed|misread+missed",
 "blind_implied": 3,
 "adjacent_defensible": true,
 "why": "两句话以内"}
```

### 3.2 阶段 B：归类（给答案）

在阶段 A 的输出基础上，告诉分析器真实等级和预测等级，让它从
`reading / target_confusion / weighting / threshold / gold_questionable / unexplained` 中选一个，
并用一句话说明理由（定义见 [00-common.md](00-common.md) §4.2）。

### 3.3 一致性检查

代码执行 [00-common.md](00-common.md) §4.3 的 K1–K6（K7 只用于 Task 2）。出现矛盾就重问一次，仍矛盾记为 `unexplained`。

### 3.4 人工抽查

从试点的 20 条里随机抽 10 条（`seed = 0`），生成一份便于阅读的 Markdown 文件：
每条依次列出动作、模型推理全文、阶段 A 和阶段 B 的输出、真实值、预测值。
用户逐条只回答两个问题：

1. 事实层判得对不对？
2. 判断层判得对不对？

## 6. 验收标准与决策

**试点能否进入正式运行：**

| 指标 | 标准 |
| --- | --- |
| 人工抽查中事实层的一致率 | ≥ 8/10 |
| 人工抽查中判断层的一致率 | ≥ 7/10 |
| 一致性检查的矛盾率（重问之前） | ≤ 20% |
| JSON 解析成功率 | 100% |

不达标就改 prompt，**新建**一个版本号的文件，不覆盖旧文件，再跑一次试点。

**正式结果怎么用：**

| 3→4 错例中「事实层为 correct」的占比 | 下一步 |
| --- | --- |
| ≥ 60% | 以尺度错误为主：[02-task1.md](02-task1.md) 优先做边界规则 + 对比示例 |
| ≤ 40% | 以理解错误为主：[02-task1.md](02-task1.md) 优先做 `facts` 输出格式，分步 prompt 提前 |
| 40%–60% | 两者都做，按 02 的默认顺序 |

`gold_questionable` 的条数单独报告。如果超过 15%，在组会上讨论标注噪声，必要时联系主办方。

## 8. 试点记录（2026-11-07）

这一节是两个早期草稿版本的试点，分析器与被审查的预测模型都是 deepseek-flash。
两版都没有达标，提示词和输出目录已删除，这里只保留它们暴露的问题，以说明 v3c 为什么那样设计：

- **v3**：阶段 A 把推理里「没提到的所有细节」都列成漏读（例如「草稿尚未发送」），第一轮矛盾率 15/20 = 75%。
  改法：每条漏读都要标明会不会改变等级，只有会改变等级的才算漏读。
- **v3b**：41 条（3→4 的 20 条 + 4→3 的 21 条）里，「相邻等级都说得通」这个是非字段全部回答「是」，没有区分力。
  改法：v3c 改为盲判时在两个候选等级里强制二选一，或明确回答「分不出」。

**初步结论（来自 v3b 的 41 条，人工抽查完成前只能算草稿）**：

1. 3→4 的 20 条里，事实都读对了，分歧在线划在哪，即尺度问题。
2. 对照组说明分析器没有简单附和预测值：4→3 的 21 条里，它有 12 条盲判为 4（即标准答案）。
   两组合起来看，分析器只看定义时**倾向于判 4**，所以定义本身就把这类情况推向 4。
3. 3 级和 4 级的区分特征**不是**单纯的「单个收件人 / 单条记录」：真实 3 级里有「单个位置卡片发给一个人」，
   真实 4 级里也有「单人行程发给无关第三方」（AGENTRISK-464）、「单个用户的支付卡信息外发」（AGENTRISK-014）。
   只靠范围写规则，必然会弄坏另一侧。
4. 限制：分析器和预测模型是同一个模型，结论 1 可能带有同一模型的偏差，需要人工抽查和换更强的分析器来核实。

## 9. Claude 分析器复测（2026-11-07，prompt v3c）

依据 [00-common.md](00-common.md) §0 的 R1–R5：分析器换成 Claude，走文件交接
（`src/agentic.py export / import`，每个阶段由另开的 Claude 子代理完成，子代理只读自己那批输入文件）。
样本与 v3b 相同：3→4 的 20 条，加上 4→3 的 21 条，共 41 条。
目录：`results/analysis/task1/20261104-082558-audit-v3c-claude/`。

**注意：这次同时改了两样东西（分析器模型，以及 prompt 从 v3b 改为 v3c），所以和 §8 的差异不能全部归因于换了模型。**

| | DeepSeek + v3b（§8） | Claude + v3c |
| --- | --- | --- |
| 第一轮矛盾率 | 0/20 与 4/21 | 6/41 = 15%，重问后全部判为 `unexplained` 并丢弃 |
| 事实层为 correct | 37/41 | **22/41** |
| 事实层 misread / missed / 两者都有 | 2 / 2 / 0 | 9 / 5 / 5 |
| 判断层 | threshold 38、reading 3 | **threshold 15、reading 13、weighting 7、unexplained 6** |
| 盲选更支持真实值 | 13/41 | **20/41（49%，接近随机）** |
| 选「分不出」 | （旧字段 41/41 为 true） | 0/41 |

分组看 Claude 的盲选：3→4 组更支持真实值 8/20，4→3 组 12/21。

**结论（人工抽查前仍是草稿）：**

1. **3/4 的线没法从现有定义里推出来。**一个更强、且与预测模型不同的分析器，盲选两个候选等级时，只有 49% 和真实值一致，与随机相当。
   所以问题不在预测模型不够聪明：要么标注者用了定义里没写的约定，要么有相当多的标注噪声。
   两种情况都说明，要靠**示例**（few-shot、对比示例）把线展示出来，单靠改写定义不够。这与 few-shot 在 Task 1 上显著有效是一致的。
2. **不全是尺度问题。**Claude 认为约三分之一（13/41）是阅读错误，例如把「住宅楼」说成「家庭住址」（AGENTRISK-040）、
   把有计划的公开录音说成「秘密录音」（AGENTRISK-686）、对可以撤销的授权说「不可逆」（AGENTRISK-312）。
   DeepSeek 作为分析器时几乎看不出这类问题，因为同一个模型不容易发现自己的误读。
3. 6 条重问后判为 `unexplained` 的样本有一个共同点：推理里的误读把等级往**高**推，预测值却偏**低**（或反过来），
   误读解释不了这个错误方向。丢弃它们是合理的。

**对计划的影响**：[02-task1.md](02-task1.md) §0 的 T2（降低 E1 预期）要放宽。阅读错误约占三分之一，
`facts-v1` 和分步 prompt 仍然值得做；但它们能修的只是这三分之一，主体仍要靠对比示例。

抽查表：`results/analysis/task1/20261104-082558-audit-v3c-claude/spot-check.md`（10 条，seed 0）。
交给另开的 Claude 会话交叉核对（审阅 prompt 是一次性工具，不进 PR，需要时再生成（2026-11-09 决定）），
用户本人至少再看 3–5 条。

## 10. 校准关卡 G1、G2（2026-11-07）

关卡定义见 [02-task1.md](02-task1.md) §0。三次运行用的 prompt 都是 v3c，样本相同（41 条）。

| 运行 | 目录（`results/analysis/task1/` 下） | 分析器 |
| --- | --- | --- |
| Opus 第 1 次 | `20261104-082558-audit-v3c-claude` | Opus 5.5，文件交接 |
| Opus 第 2 次（G2） | `20261104-082558-audit-v3c-claude-run2` | Opus 5.5，新的子代理，看不到第 1 次的结果 |
| DeepSeek（G1） | `20261104-082558-audit-v3c-deepseek` | deepseek-flash，API |

**两两一致率：**

| 对比 | 事实层（读对 / 没读对） | 盲选更支持的等级 | 最终判断层 |
| --- | --- | --- | --- |
| Opus 1 vs Opus 2 | 33/41 = 80% | 33/41 = 80% | **26/41 = 63%** |
| Opus 1 vs DeepSeek | 23/41 = 56% | 24/41 = 59% | 15/41 = 37% |
| Opus 2 vs DeepSeek | 19/41 = 46% | 20/41 = 49% | 10/41 = 24% |

**各次运行自己的分布：**

| 运行 | 读对 | 判断层 | 盲选 = 真实值 |
| --- | --- | --- | --- |
| Opus 1 | 22 | threshold 15、reading 13、weighting 7、unexplained 6 | 20/41 |
| Opus 2 | 20 | threshold 11、reading 13、weighting 9、unexplained 8 | 22/41 |
| DeepSeek | 38 | threshold 27、weighting 13、reading 1 | 13/41 |

**G1 结论**：同一个 v3c prompt 下，DeepSeek 和 Opus 的分歧很大（判断层只有 24–37% 一致），
DeepSeek 几乎看不出阅读错误，盲选也偏向它自己的预测（4 级）。所以 §8 和 §9 的差异主要来自**分析器模型**，不是 prompt。
DeepSeek 不适合做分析器。

**G2 结论：没过（63% < 70%）。**但两次 Opus 运行在阶段 A 上是稳定的（事实层、盲选都是 80% 一致）。不稳定集中在阶段 B 的归类。15 条分歧的构成：

| 分歧 | 条数 | 原因 |
| --- | --- | --- |
| threshold ↔ weighting | 4 | 这两类只差「盲选是否等于真实值」，而盲选与真实值的一致率只有约 50%，接近随机。这个区分本身就是噪声 |
| 事实层一次读对、一次读错，导致的判断层分歧 | 8 | 有几句说法处在「算不算有依据」的边界上 |
| 涉及 unexplained 的分歧 | 6 | `unexplained` 基本都是同一种情况：推理里有一句没依据的话，但它推动等级的方向和模型实际出错的方向相反，所以解释不了这个错误 |

（以上 3 行有重叠，合计超过 15。）

两次 Opus 运行都稳定成立的结论：

1. 盲选与真实值的一致率是 20/41 和 22/41，**两次都在 50% 左右**。也就是说，3/4 的线从定义里推不出来。这一条最稳。
2. 两次都有 13 条被归为阅读错误，其中 9 条是同一批样本。阅读错误大约占三分之一，这一条大体稳定。

**建议的分类修改（v3d，尚未实施，需要用户确认）：**

1. **把 `threshold` 和 `weighting` 合并成一类「尺度」（scale）。**理由：这两类的区分依赖盲选，而盲选对真实值是随机水平，区分不可靠。
   事后按合并后的分类重算，两次 Opus 运行的一致率是 30/41 = **73%**，能过 70% 的关卡（这是事后重算，不是新跑出来的，只能作参考）。
2. **对没依据的说法，也要标 `moves_level`**，和 v3b 对漏读事实的处理一样：只有会改变等级的错误说法，才让事实层变成 misread。
   这样，「有一句错话但不影响结论」的样本会归入尺度类，不再落到 `unexplained`。按这个口径事后重算，一致率是 33/41 = 80%。

## 11. G3 结果与 v3d 方案（2026-11-07）

**G3 未过。**审阅者 Opus 5 与分析器 Opus 5.5 在事实层上一致 7/10（标准 8/10），在判断层上一致 5/10（标准 7/10）。
审阅结果见 `results/analysis/task1/20261104-082558-audit-v3c-claude/spot-check-review.md`。

主要问题与 G2 指向同一个根源：**「漏读」没有定义清楚。**模型的推理已经表明它知道某件事（例如写了「外部邮件驱动、没有审批」），
只是没逐字写出「用户只要求读取」，阶段 A 就把它标成漏读，阶段 B 随即归为 `reading`。
审阅者认为这类样本（467、499，存疑的 464）其实是「读到了但分量不够」，应归为尺度问题。

其他发现：

- 同类内容上，盲选等级不一致：302、323 判为更支持 3，375 内容几乎相同却判为更支持 4。这本身印证了「3/4 的线定义不出来」，不是新问题。
- 登记瑕疵：357 把推理里已经写到的事实列成了「没提到的事实」。

人工审核题见同目录的 `human-review.md`。第 1 题是定义题，**v3d 要等用户回答后再定稿**。

### v3d 方案（这一版是分析器的最后一版）

| 修改 | 内容 | 针对的问题 |
| --- | --- | --- |
| 1 | 「漏读」只指推理**既没写出、也没有任何说法表明它知道**的事实。换个说法表达出来、或从其他说法能看出它已经知道的，都算读到了（以第 1 题的回答为准） | G2 中 8 条事实层不稳定；G3 的 467、499、464 |
| 2 | 没依据的说法也要标 `moves_level`；只有会改变等级的错误说法，才让事实层变成 misread | G2 中 6 条 `unexplained` |
| 3 | `threshold` 和 `weighting` 合并为 `scale`（尺度）；判断层只剩 `reading`、`target_confusion`、`scale`、`gold_questionable`、`unexplained` | G2 中 4 条 threshold ↔ weighting 分歧；这个区分依赖的盲选只有随机水平 |
| 4 | 新增机械检查 K9：列为「没提到」的事实，如果它的主要内容已经出现在推理原文里（忽略大小写），算矛盾 | G3 的 357 |

### 验收与停止规则

1. 用 v3d 跑两次独立的 Opus 5.5（G2），再请 Opus 5 审阅同样 10 条（G3），加上用户对 `human-review.md` 的回答。
2. 通过标准：两次运行按「读错 / 尺度」两大类的一致率 ≥ 70%；G3 的判断层一致 ≥ 7/10。
3. **v3d 是最后一版，不再迭代 prompt。**如果仍不通过：分析器只用于「两次运行都判为读错」的高置信样本，把这些交给 trace2skill；
   其余全部当作尺度问题，交给示例处理。规则到底有没有用，由修复循环的回测和 train_val 上的结果来判断。

## 12. v3d 结果（2026-11-07）：审查对象改为 facts-v1 的输出

按用户的意见，「知道 / 不知道」改成看模型自己写了什么：先跑 facts-v1（输出 FACTS + JUDGMENT），
再用 v3d 审查它的错例。规则是：FACTS 或 JUDGMENT 用任何措辞写到了就算知道，都没写到才算不知道。
因此 `human-review.md` 里关于「算不算漏读」的人工题不再需要回答。

| | reason-v1 | facts-v1 |
