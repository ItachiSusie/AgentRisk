# 组会讨论稿 2026-11-11（11/05 – 11/10）

数据：dev 143 条只作最终测试；train_evolve 461 条用来诊断和蒸馏；train_val 107 条做中间验证。预测模型都是 `deepseek-flash`，温度 0。
指标：Task 1 用 MAE（Mean Absolute Error，平均绝对误差），越低越好；Task 2a / 2b 用 Mean Jaccard（平均杰卡德相似度，预测和真实标签集合的交集除以并集），越高越好。
显著性用配对自助法（paired bootstrap，逐条配对后重抽样看差值置信区间是否跨 0）。dev 143 条下，差值小于约 0.03 基本是噪声。

---

## 0. 一句话

1. 拆成三个单任务比一个多任务好。
2. oracle 上限实验（把一个任务的标准答案告诉另一个任务）说明 2a 和 2b 互相帮助很小，所以不值得把它们合并成一个联合任务。
3. 盲测探针说明 Task 1 的 3/4 级错误主要是「线划在哪」的问题，不是读不懂轨迹。
4. 补上官方定义后：模型能认出原来认不出的标签，但 Task 1 的 3/4 边界纹丝不动。
5. 选哪种输出格式，影响可能比蒸馏规则更大。

## 1. 单任务 vs 多任务

**为什么做**：原来是一个 prompt 一次预测三个字段（多任务）。想知道拆成三个独立任务（每次只预测一个字段）会不会更好。

**结果**（dev，zero-shot，来源 `results/SUMMARY.md`）：

| | Task 1 MAE ↓ | Task 2a ↑ | Task 2b ↑ | 三字段全对 ↑ |
| --- | --- | --- | --- | --- |
| 多任务 无推理 | 0.301 | 0.811 | 0.726 | 49.0% |
| 多任务 有推理 | 0.238 | 0.821 | 0.740 | 49.7% |
| 单任务 有推理（拼回三字段） | 0.238 | 0.832 | 0.753 | **55.2%** |

- 单任务 + 有推理的「三字段全对」比两种多任务都**显著**更好，约高 6 个百分点。
- 「有推理」指先写一段不超过 120 词的依据再给标签。它对 Task 1 帮助最大，无推理和有推理的 MAE 分别是 0.266 和 0.238。

**结论**：后面都按单任务做。

## 2. oracle 上限实验：2a 和 2b 之间有没有依赖

**为什么做**：
- 如果知道风险领域（2a）能大大帮助判断驱动因素（2b），或者反过来，就值得把 2a、2b 合并成一个联合任务，或者串起来预测。
- 所以做了一个上限实验：在输入里**直接给出另一个任务的标准答案**，看分数最多能涨多少。
- 这是理想情况，实际预测时拿不到标准答案。所以如果这样都涨不多，合并就没有意义。
- 实现：`src/make_oracle_splits.py` 生成带答案的数据，prompt 为 `answer-v3` / `reason-v3`。

**结果**（zero-shot，同一时间重跑 v1 作对照，单位 Mean Jaccard）：

| 任务 | 线 | 数据 | 不给答案 v1 | 给另一任务答案 v3 | 差值 |
| --- | --- | --- | --- | --- | --- |
| 2a（给 drivers） | answer | train_val | 0.799 | 0.824 | +0.025 |
| 2a | answer | train_evolve | 0.822 | 0.794 | **−0.028** |
| 2a | reason | train_val | 0.838 | 0.860 | +0.022 |
| 2a | reason | train_evolve | 0.809 | 0.834 | +0.025 |
| 2b（给 domains） | answer | train_val | 0.625 | 0.631 | +0.006 |
| 2b | answer | train_evolve | 0.675 | 0.701 | +0.026 |
| 2b | reason | train_val | 0.681 | 0.668 | −0.013 |
| 2b | reason | train_evolve | 0.738 | 0.738 | 0.000 |

（run_id 都在 `results/_smoke/task2{a,b}/zero-shot-{answer,reason}-v{1,3}/20261110-0303xx`。这里的分数由预测文件直接算出，还没有生成 metrics.json。）

**结论**：
- 即使直接告诉模型另一个任务的**正确答案**，最多也只涨约 0.025，有两格反而下降。
- 也就是说，2a 和 2b 对彼此的信息量很小，两个任务基本独立。
- 所以**否定「把 2a、2b 合并或串起来做」的思路**：上限只有这么高，实际用的还是模型自己预测的（会出错的）另一个标签，收益只会更小。

## 3. 盲测探针：Task 1 的错误是「读错了」还是「线划得不一样」

**为什么做**：
- Task 1 的误差主要来自 3 级和 4 级之间的混淆。在 train_evolve 上，真实 3 判成 4 的有 34 条，真实 4 判成 3 的有 21 条。
- 这类错误有两种可能，对应的改法完全不同：

| 错误类型 | 含义 | 对应的改法 |
| --- | --- | --- |
| 理解错误 | 事实读错了或漏读了 | 让模型更仔细地读：先列事实再判断（facts 格式） |
| 尺度错误 | 事实都读对了，只是 3/4 的线和标注者划得不同 | 把线展示出来：边界规则、对比示例 |

**做法**：
- 让一个更强的分析器（Claude Opus 5.5）审查预测模型的推理。
- **先不告诉它答案**：推理里的等级词全部遮掉，让它逐条检查事实有没有依据，再在两个候选等级里自己二选一（盲选）。
- 之后才告诉它答案，让它对错误归类。
- 详见 `docs/agentic-distill/01-blind-probe.md`。

**结果**（41 条样本，Opus 跑了两次）：

| | 结果 |
| --- | --- |
| 盲选与真实等级一致 | 20/41 和 22/41，**约 50%，相当于随机** |
| 被判为阅读错误 | 两次都是 13/41，**约三分之一**（其中 9 条是同一批） |
| 其余 | 尺度问题：事实读对了，分歧在线划在哪 |

（扩大到全部错例后，盲选命中率 Task 1 为 64–69%，2a 为 60–63%，2b 为 61%。）

**结论**：
1. **主体是尺度问题**：比预测模型更强的分析器，只看定义去判 3 还是 4，也只有一半猜对。说明这条线不在定义的文字里，要么是标注者的约定，要么是标注噪声。所以要靠示例把线展示出来，单改定义不够。这也解释了为什么 few-shot 在 Task 1 上有效。
2. **约三分之一是阅读错误**，例如把「住宅楼」说成「家庭住址」，把可撤销的授权说成「不可逆」。这部分 facts 格式能修。
3. 换用 deepseek 自己当分析器，几乎看不出阅读错误。同一个模型不容易发现自己的误读，所以分析器必须用更强的、不同的模型。

## 4. facts 格式 + 智能体式蒸馏（Task 1 / 2a / 2b）

**做什么**：
- facts 格式：模型先从轨迹里逐字引用 2–6 条事实，再写判断，最后给标签。代码会检查引文是否真出自轨迹。
- 智能体式蒸馏（agentic distillation）：分析器诊断 train_evolve 上的错例，写规则补丁，在 train_evolve 上回测，合格的才合并进 prompt。最后得到 facts-v2。

**结果**：

| 任务 | train_evolve：v1 → v2 | dev zero-shot：v1 → v2 | dev BM25 k=10：v1 → v2 |
| --- | --- | --- | --- |
| Task 1（MAE ↓） | 0.298 → **0.228**（显著） | 0.238 → 0.182（置信区间跨 0） | 0.210 → 0.210 |
| Task 2a（↑） | 0.843 → 0.871 | 0.824 → 0.840（噪声） | 0.851 → 0.859（噪声） |
| Task 2b（↑） | 0.754 → 0.793 | 0.737 → 0.741（噪声） | 0.760 → 0.751（噪声） |

**结论**：
- 规则在 train_evolve 上都有效，但迁移不到 train_val 和 dev。Task 1 在 dev 上方向最好，但仍不显著。
- 2a / 2b 的错误多数是「选标签」问题，规则能帮的有限：
  - 2a 常见的是该选两个只选了一个；
  - 2b 常见的是把「范围越界」判成「授权失败」。
- 代码已推到分支 `feat/facts-agentic-distill`。

## 5. 补上官方定义后重跑 zero-shot

**为什么跑**：
- 11/10 核对官方任务页时发现，官方给每个标签写的描述（Description）**从来没有进过任何一版 prompt**：
  - 2a 的 11 个领域、2b 的 7 个驱动因素，prompt 里只有标签名；
  - Task 1 是一版自己压缩的描述，还丢了关键判据。例如官方的 3 级就包含「涉及敏感目标」，压缩版删掉了这一条，导致模型一看到敏感目标就判 4。
- 也就是说，之前所有实验都是在「只知道标签叫什么、不知道标签是什么意思」的条件下做的。
- 所以给三种输出格式都补上官方定义，重跑 zero-shot：answer-v4、reason-v4、facts-v3。

**结果**（dev，zero-shot；详见 `docs/definition/00-common.md` §7）：

| 任务 | answer v1 → v4 | reason v1 → v4 | facts v1 → v3 |
| --- | --- | --- | --- |
| Task 1（MAE ↓） | 0.266 → 0.280 | 0.238 → **0.224** | 0.238 → 0.245 |
| Task 2a（↑） | 0.837 → 0.840 | 0.832 → 0.803 | 0.824 → **0.854** |
| Task 2b（↑） | 0.711 → 0.733 | 0.753 → 0.751 | 0.737 → **0.753** |

**说明了什么**：
1. **定义能让模型认出原来认不出的标签**：
   - 2a 的「法律」召回率从 0.077 涨到 0.308；
   - 2b 的「范围越界」召回率从约 0.2 涨到约 0.5。
2. **但改不动 Task 1 的 3/4 边界**：真实 3 判成 4 的条数从 52 变成 53，纹丝不动。这和盲测探针的结论一致。
3. **总分不变不等于没变化**：2b 的「范围越界」修好了，但「授权失败」的召回率掉了，正好抵消。只看总分会漏掉这件事。
4. **定义也有副作用**：Task 1 的官方描述每一级都用「或」串了多个条件，给了模型更多升级的理由。结果 1 级的正确率从 0.953 降到 0.926。
5. **只有 answer 线的改善显著**（2a、2b 在 train_evolve 上）：不写推理的模型最依赖标签的含义，所以定义对它帮助最大。
6. **意外发现：facts 格式在 Task 1 上本身就是退步**：train_evolve 上 reason-v1 是 0.247，facts-v1 是 0.299。facts-v2 蒸馏后的 0.228 基本只是把这部分损失补了回来。所以选哪种输出格式，影响可能比蒸馏规则更大。

## 6. 下一步方向（供讨论）

| 任务 | 下一轮的起点 | 重点 |
| --- | --- | --- |
| Task 1 | reason-v4 | 3/4 边界靠对比示例而不是规则；保护 1 级判断不被弄坏 |
| Task 2a | facts-v3 | 单个还是多个标签的问题（cardinality，占错例一半以上，定义帮不上） |
| Task 2b | reason-v4 | 把「授权失败」召回率拉回 0.96 左右，同时不让「范围越界」退回去 |

其他问题：
- **几条老规则要作废**：v2 的规则是在没有定义的情况下学出来的，只当参考。
- **诊断工具要适配 reason 格式**：现在的工具是为 facts 格式设计的，引文可以用代码直接核对；reason 是自由文本，没法这样核对。在 reason 上做蒸馏，需要先定一个审查办法。
- **回测标准**：facts-v1 自己重跑一次，就会让某些标签波动超过 5 个百分点。建议先重跑 2–3 次，估出每个标签的正常波动，再定接受标准。
- **数据层面**：3/4 边界连强模型盲选都只有 50%，值得讨论这里是否有标注噪声，以及能否和标注方确认判据。
- **示例改进**：few-shot 示例目前只给标签，可以试试示例里也带上事实列表或推理。
